# 6. Evaluation, Discussion and Conclusions
## 6.1 Evaluation Process
The evaluation of this project was conducted through systematic Postman-based API testing documented in Appendix 2, covering fifty-seven individual test cases across all core subsystems: authentication, notes, events, ICS import and export, account deletion, user settings, and university timetable synchronisation. This approach was selected because the most critical success criteria were the reliable and secure operation of the backend API endpoints, given that the entire Privacy-by-Design architecture depended on the correct behaviour of the AES-128 encryption cycle, the session management middleware, and the GDPR-compliant account deletion cascade. Testing directly against these endpoints provided the most direct and repeatable mechanism for verifying that the system met its defined requirements.

Each system was evaluated against the functional requirements labelled in Section 4.1. with each test case designed to both verify the expected success condition and the appropriate handling of invalid or boundary inputs. For example, the notes numerous tests successfully validated the decrypted GET response confirming that no plaintext persisted beyond the backend server memory. Similarly, the account deletion tests verified that ON DELETE CASCADE correctly propagated across all dependent tables, confirming compliance with the right of erasure under article 17 of GDPR. The timetable synchronisation tests confirmed core feasibility with integration by web scraping the presentation layer of the university’s legacy-like timetable system.

However, as discussed in Section 5.3, the pivot to sprint-based development meant that runtime debugging substituted for a formal automated testing framework such as Jest throughout the development lifecycle. This carries an inherent risk that edge-case behaviour within individual functions, particularly within the AES-128 encryption module and the TF-IDF algorithm, may have gone undetected, and represents a limitation of the current evaluation coverage that would need to be addressed in any future iteration of the project.

Nonetheless, the successful verification of all fifty-seven test cases across the core subsystems demonstrates that the system reliably automates the extraction and management of timetable and scheduling data, directly evidencing that the primary aim of reducing the manual data entry burden, and by extension the preventable academic stress identified in the literature, has been met.
## 6.2 Diversity, Equality & Inclusion
The project engaged with DEI considerations from its creation, driven by ethical obligations of the problem space itself. As identified in Section 2.1. students with specific learning needs such as dyslexia are disproportionately impacted by the cognitive demands of maintaining manual schedules, as established by Abbott-Jones (2021). This was a deliberate focus during project planning and design as to cater uniformly to students who both do and do not struggle with manual scheduling without it being burdensome.

In terms of accessibility, the post-MVP project utilises user settings, introduced to support themes being light, and dark mode, while also allowing for an auto mode dependent on the user's current browser theme. Font size and format preferences were similarly proposed through the user settings system, however, were unable to be added in time.

However, the timetable scraper is tightly coupled to the specific HTTP based authentication utilised and table formatting for UCLan’s TimeTable system, which limits institutional inclusivity of the applications. Students are other universities would be unable to benefit from the automatic timetable scraping. Supporting a broader range of timetable login systems for different institutions, or in the event of being unable to scrape, offering the manual ICS import as a fallback would significantly improve the inclusivity of the solution in future. Additionally, the React frontend has not been evaluated against the Web Content Accessibility Guidelines (Kirkpatrick et al., 2018), which define the internationally recognised standard for web accessibility covering visual, auditory, motor, and cognitive disabilities, and ensuring conformance would be a necessary extension for any production deployment intended to serve students with disabilities.
## 6.3 Evaluation Discussion
The primary aim of this project was to develop a web-based adaptive student study planner that removes the need for manual data entry for timetables, thereby reducing the preventable academic stress caused by disorganisation.

Objectives 1 and 2 were largely achieved. The investigation confirmed that the university timetable system lacked any publicly accessible API endpoints, necessitating the wrapping strategy described by Bisbal et al. (1999), and the custom backend scraper successfully authenticated into the legacy system and parsed timetable events into the database, definitively proving the viability of the integration. The ICS import and export functionality further addressed Objective 1 by providing a universally compatible pathway for third-party calendar data. Objectives 3 and 4 were fully met; the AES-128 encryption-at-rest architecture, UUID-derived key derivation, bcrypt password hashing, and ON DELETE CASCADE account deletion together constitute a robust Privacy-by-Design implementation compliant with UK GDPR and the Data Protection Act (2018). Objective 5 was fully achieved and validated through twelve dedicated test cases. Objective 6 was partially met; synchronisation was implemented as a user-triggered request rather than the fully automated time-interval background service originally specified. Objective 7 was met through the React SPA dashboard, which aggregates recent notes, upcoming events, and a calendar view into a unified interface. Objective 8 was partially met; comprehensive Postman testing was conducted across all API subsystems, however the absence of a formal automated unit testing framework means coverage falls short of the comprehensive unit testing originally specified.

The one objective entirely descoped was the OCR feature planned under Objective 1. As discussed in Section 5.1, this decision was made deliberately to prioritise the reliable completion of the core backend features within the available timeframe, and the ICS import pathway provides an alternative mechanism for importing external schedule data.

The system demonstrably removes the need for manual timetable entry through automated synchronisation, provides a secure GDPR-compliant notes and events platform, and directly reduces the scheduling burden that Pascoe, Hetrick and Parker (2019) and Pérez-Jorge et al. (2025) identify as a significant contributor to academic stress and impaired executive functioning. To the question of whether the artefact solves the problem it set out to solve, the answer is substantially yes; the core problem of manual timetable data entry has been eliminated for the target demographic, and the unified dashboard addresses the disorganisation cycle described in the literature review.

In terms of commercial viability, the timetable scraper is tightly coupled to UCLan's authentication mechanism and HTML table structure, requiring rearchitecting for deployment at other institutions. A configurable integration layer abstracting the scraping logic behind an institution-agnostic interface would be necessary for any wider commercial deployment. The subscription-based freemium model outlined in the original proposal, centred on daily note limits, remains architecturally feasible given the existing server-side session and settings infrastructure.
## 6.4 Critical Reflection
The project’s methodology underwent significant changes from the originally proposed to final delivery. The initial waterfall approach outlined in section 3 proved appropriate for the requirements gathering, security-planning, and initial design phase, as these foundational stages were required in the sequential process before any meaningful implementation could proceed. However, the transition to frontend development revealed limitations of maintaining a strictly sequential methodology. As discussed in section 4.2, the decision to pivot from the Vanilla JavaScript to React introduced fundamental architectural changes that were not initially anticipated during planning phases due to inexperience with the React Framework, forcing an adaptive shift from Waterfall to a sprint-based development approach, with concurrent testing rather than deferred validation as originally planned.

In retrospect, this methodology change was essential to the project's success, though it came at a considerable cost. The React migration, while ultimately producing a significantly more maintainable and scalable frontend architecture, consumed development time that had been allocated to feature expansion. Due to React being a technology without prior experience, the time also had to account for the learning curve, which was initially underestimated when learning custom hooks, contexts, state management, and the component lifecycle. Consequently, the OCR functionality initially planned under Objective 1 was deliberately descoped to prioritise reliable completion of the core timetable integration, note-taking and calendar subsystems. This was the correct decision given the project's time constraints, as attempting to implement all originally envisioned features would have risked delivering a partially functional system rather than a robust final product for the show and tell. Supervisor feedback during the MVP demonstration validated this pragmatic approach, confirming that establishing solid foundational functionality was more valuable than pursuing feature completeness at the expense of system stability.

From a technical perspective, the project built upon foundational concepts from previous year's work in Flutter, particularly around state management. However, applying these concepts to a React and Node.js stack required significant adaptation. The practical challenges encountered, particularly implementing HTTP basic authentication for the timetable scraper, choosing a stable library for handling AES-128 cryptographic data flow for encryption-at-rest, and mastering React's hook-based state management, forced deeper engagement with these technologies than any academic coursework had previously demanded. The authentication flow implementation, detailed in Appendix 4, exemplifies this progression; designing the AuthProvider context pattern and the protected routing system required synthesising knowledge from disparate sources and online information to deduce a workable system. The TF-IDF algorithm was straightforward to implement; however, as discussed in Section 5.2, queries consisting primarily of stop words presented an edge case. Standard tokenization filters common terms during preprocessing, causing such queries to return zero results. The implementation addresses this through fallback tokenization that retains stop words when the filtered query produces no terms, alongside post-calculation bonuses for exact title matches, partial title matches, and content matches to ensure relevant notes surface regardless of stop word presence.

However, the project also exposed areas requiring further development. Time estimation for unfamiliar technologies proved consistently optimistic; the React migration alone took nearly double the allocated timeframe, a miscalculation that cascaded through subsequent sprint planning. Additionally, while the systematic Postman-based API testing documented in Appendix 2 provided comprehensive backend validation, the absence of automated frontend testing represents technical debt that would need addressing in any production deployment. The reliance on runtime debugging rather than a formal testing framework such as Jest, while pragmatic given the time constraints, meant that regression testing was manual and potentially incomplete. Edge-case behaviour within individual React components, particularly those handling asynchronous state updates in the calendar view, may have gone undetected without comprehensive unit test coverage.
## 6.5 Conclusions and Further Work
This project successfully achieved its primary aim of developing a web-based adaptive student study planner that eliminates manual timetable data entry through automated synchronisation. The delivered system demonstrably addresses the core problem identified in the literature review: the preventable academic stress and impaired executive functioning caused by the disorganisation cycle that Pascoe, Hetrick and Parker (2019) and Pérez-Jorge et al. (2025) establish as significant contributors to student wellbeing deterioration. Seven of the eight project objectives were substantially met, with the secure GDPR-compliant architecture, automated timetable scraping, comprehensive note management system, and unified dashboard all functioning reliably as verified through the fifty-seven test cases documented in Appendix 2.

The OCR functionality planned under Objective 1 remains the most significant piece of descoped work requiring future implementation. Integrating Tesseract.js or a comparable optical character recognition library would enable students to upload examination timetable images and automatically extract relevant dates, completing the originally envisioned feature set. However, as discussed in Section 5.1, the deliberate decision to prioritise core functionality over feature completeness ensured the delivery of a robust and reliable foundation upon which such enhancements can be built.

Further work beyond OCR would need to address the institutional portability limitations identified in Section 6.2. The current timetable scraper implementation is tightly coupled to UCLan's specific HTTP basic authentication mechanism and HTML table structure, requiring substantial rearchitecting for deployment at other institutions. Developing a configurable integration layer that abstracts the scraping logic behind an institution-agnostic interface would be essential for commercial viability, potentially using a plugin-based architecture where each institution-specific parser implements a common interface. Additionally, the client-side TF-IDF search algorithm, while preserving privacy by operating exclusively on decrypted in-memory notes, presents scalability limitations as note volume increases. Future iterations could explore server-side search implementations using homomorphic encryption or secure enclaves to maintain privacy guarantees while offloading computational burden from the browser.

The absence of automated frontend testing represents technical debt that would require addressing in any production deployment. Implementing a formal testing framework such as Jest with comprehensive component-level unit tests would ensure regression coverage currently missing from the manual runtime debugging approach. Similarly, the React frontend has not been evaluated against Web Content Accessibility Guidelines (Kirkpatrick et al., 2018), and ensuring WCAG conformance would be necessary for any deployment intended to serve students with disabilities. Production deployment would also require proper HTTPS configuration with valid SSL certificates to secure data transmission between client and server, as the current development environment operates over HTTP, except for HTTPS requests made by the timetable web scraper to the university system.
