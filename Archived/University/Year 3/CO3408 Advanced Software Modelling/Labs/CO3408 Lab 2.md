# Lab Tasks
## Lab Objectives
1) Write Pre-Conditions & Post-Conditions
2) Define Class Invariants to ensure object consistency
3) Apply Design by Contract (DbC) principles to small classes
4) Gather system requirements and design a simple state transition diagram

>[!EXAMPLE] Task 1 - BankAccount - Deposit & Withdraw Methods
> > [!Scenario]
> > Implement a BankAccount class with deposit & withdraw methods
> 
> >[!Requirements]
> >- despoit(amount) - increases balance by amount.
> >- withdrawal(amount) - decreases balance by amount if sufficient funds exist
>
> >[!Instructions]
> >1) Write Pre-Conditions & Post-Conditions for **both** methods
> >2) Use Design by Contract style (JML-Style comments or Pseudo-code)
>
> > [!EXAMPLE]
> > ```java
> > /*@ requires amount > 0;
> > @ ensures balance == \old(balance) + amount
 >>@*/
> >public void deposit(int amount)
> >{
> >	// Implementation
> >}
> > ```
> 

> [!EXAMPLE] Task 2 - Class Invariants
> > [!Requirements]
> > Use the BankAccount from Task 1
>
> > [!Instructions]
> > 1) Define a class invariant to ensure the balance is never negative.
> > 2) Explain why maintaining this invariant is important.
> > > [!Hint] Example
> > > ```Java
> > > //@ invariant balance >= 0
> > > ```

> [!EXAMPLE] Task 3 - MinMax Class Specification
> > [!Scenario]
> > Implement a MinMax class to find the minimum and maximum of an array.
>
> > [!Instructions]
> > 1) Specify Pre-Conditions must not be empty.
> > 2) Specify Post-Conditions
> >    - Min returns the smallest element
> >    - Max returns the largest element
> > 3) Optionally, define a class invariant if application
> > [!Hint] Example

> [!EXAMPLE] Task 4 - ATM and Bank
> >[!QUOTE] Scenario
> >You are modelling a simple Bank ATM system that allows customers to perform standard banking operations. The system’s behaviour depends on its current state and user actions (events).
>
> >[!Instructions]
> > > [!EXAMPLE] Step 1 - Gather System Requirements (Provided)
> > > List the main operations the ATM can perform.
> > >
> > >- Insert Card
> > >- Enter Pin
> > >- Withdraw
> > >- Deposit
> > >- Eject Card
> > > > Refer to system requirements document for operation descriptions.
> >
> > > [!EXAMPLE] Step 2 - Identify Main System States (Provided)
> > > Determine the key system states involved in ATM operation:
> > > - Idle - waiting for card
> > > - Card Inserted - card detected, awaiting PIN
> > > - Pin Entered - authenticated user session active
> > > - Transaction In Progress - performing withdrawal or deposit
> > > - Out of Service - ATM unavailable due to fault or maintenance.
> >
> > > [!EXAMPLE] Step 3 - Draw the State Transition Diagram
> > > Create a UML state diagram that shows:
> > > - States as rounded rectangles (nodes).
> > > - Transitions as labelled arrows representing events or operations.
> > >
> > > Your diagram should include (at a minimum):
> > > - InsertCard -> Moves Idle -> Card Inserted
> > > - EnterPIN -> Moves Card Inserted -> PIN Entered
> > > - Withdraw or Deposit -> Moves PIN Entered -> Transaction in Progress
> > > - EjectCard -> Returns System to Idle
> > > - Error -> Moves Transaction in Progress -> Out of Service
> > > - MaintenanceDone -> Moves Out of Service -> Idle
> > > >[!Hint]
> > > > Use start/end symbols to mark system start in "idle" and termination if required.
> >
> > > [!EXAMPLE] Step 4 - Specify Pre-Conditions and Post-Conditions
> > Choose one operation and formally express its precondition and postcondition to show how it affects system state. 
> > > > [!EXAMPLE] 
> > > Operation: WithdrawCash 
> > > Precondition: balance >= amount && currentState == PINEntered 
> > > Postcondition: balance = old(balance) - amount && currentState = Idle
> >
